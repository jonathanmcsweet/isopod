usage: isopod account <setup|status|teardown|rules>

The sandbox account is an OPT-IN hard network boundary: boxes run under a
dedicated unprivileged account that owns nothing, and the host kernel drops
that account's traffic to private address space. Unlike the in-box ruleset
(--guest-egress), nothing inside a box — including root gained by an exploit —
can remove these rules, and they still apply to a process that escaped the box.
The engine stays rootless; root is used once, to load a static rule.

  setup     one-time, as root: create the account (subordinate ids, linger,
            home for its image store), load the firewall rules, install the
            boot persistence unit and a sudoers grant scoped to the engine
            binary. Idempotent — safe to re-run; re-applies rules after a
            firewall reload.
  status    what is and is not in place, including whether the rules are
            loaded and their drop counters.
  teardown  remove the rules, unit and sudoers grant (as root). Add --purge
            to also delete the account and its image store.
  rules     print the ruleset setup would load.

  sudo isopod account setup
  isopod account status
  isopod create devbox --account     (after setup; stage 2 of this feature)

Boxes created with --account share the account's image store: one base image
plus a thin layer per box. Existing boxes are unaffected until migrated.

Trade-offs: every account box shares one firewall identity (per-box rules are
a guest-layer concern); `egress lan-allow` on an account box needs sudo for
the host half; Linux + podman only. Override the account name with
ISOPOD_ACCOUNT (default: sandbox).
